# Hook latency release gate

The release budget is **p95 < 150 ms for installed wrappers and in-process checks** on every host on the documented fast paths: ordinary PreToolUse, unrelated projects, Stop and edit without jobs, unchanged PostToolUse, and cached checker summaries at compact. The direct subprocess check requires **hook p95 minus bare-interpreter p95 < 150 ms** and **hook p95 < 300 ms**. This removes machine-dependent startup cost from the hook-work budget while retaining an end-to-end ceiling. Equality fails. Correct hook output is required regardless of timing. When `RO_HOOK_PYTHON` resolves to the interpreter already running the installed wrapper, the runner executes the hook in that process. A watchdog thread enforces the nine-second deadline with `os._exit`, so stalled Python work cannot keep the hook alive. Other interpreter selections and library calls retain the supervised child.

## Evidence and measurement

The [baseline-adjusted Windows check](evidence/hook-subprocess-baseline.json) on Python 3.12 measured subprocess p95 of 116.7 ms and bare-interpreter p95 of 25.3 ms: 91.4 ms overhead, leaving 58.6 ms below the fixed 150 ms overhead budget. The reported CI failures at 159.5 and 165.5 ms include startup but have no matching baseline, so they cannot establish CI overhead. They motivate measuring that baseline on each runner; the 300 ms absolute ceiling leaves 134.5 ms above the larger reported CI total while still rejecting large end-to-end regressions. The installed-watchdog CI values of 57–60 ms measure a different path and are not interpreter baselines.

The [current local measurements](evidence/hook-fast-paths.json) (2026-10-28) keep the fast paths within the 150 ms budget. On Windows Python 3.12, POSIX sh p95 costs were 29.392 ms for unrelated projects, 33.259 ms for Stop without jobs, 29.002 ms for edits without jobs, 123.240 ms for unchanged PostToolUse, and 106.462 ms for ordinary shell checks. Native cmd costs were 38.977, 25.584, 23.968, 51.628 and 104.169 ms respectively. The compact checker summary lookup alone measured 24.941 ms in process against 1.4 MB discovery and 0.5 MB handoff fixtures (the 6.0.2 tree measures the same; an earlier 1.872 ms sample predates content stamps); that figure excludes the rest of SessionStart. A full startup SessionStart, whose checker reruns and hashes a reviewed two-file directory, measured 157.505 ms through sh and 156.293 ms through cmd. It is not a fast path, so the 150 ms gate does not apply; it shows the startup cost inside the nine-second hook deadline. These synthetic calls invoked no agent host and establish no Linux/macOS performance or host-delivery result.

Reproduce the local measurements with `python scripts/measure_hook_fast_paths.py --output <measurement.json>`. Each wrapper batch includes shell startup and JSON output. Stop and edit shortcuts require both the primary and recovery job registries to be absent. Compact reuses the checker summary only when dependency stamps and the calendar day match; live jobs and observation freshness are still checked. The retained [historical table](evidence/hook-latency-gatefix.json) records older supervisor batches at 183.4, 178.3 and 202.1 ms; they exceed the restored target and are not current measurements.

The subprocess gates warm caches twice, take 20 samples per batch, compute nearest-rank p95 from all samples, and compare the median of three batch p95s with the applicable budget. The direct-child test interleaves bare `python -E -S -c "pass"` starts with hook calls using the same flags, pipes and sampling scheme, then subtracts the two aggregate p95s. The in-process check takes 100 samples and uses nearest-rank p95. Ordinary PreToolUse runs against large synthetic discovery and handoff histories. Separate deterministic tests reject any attempted history reads through pathlib, `io.open`, or builtin `open`; passing a timing gate alone does not prove histories were skipped.

Timing tests carry `@pytest.mark.latency`; default pytest and the release validator exclude them. Run them separately with `python -m pytest -q -m latency tests/test_ro_cli.py tests/test_ro_hooks.py`. A separate CI step runs the marked installed-runner and direct/in-process checks on Windows, Linux and macOS. With `RO_LATENCY_REPORT`, the JSON keeps installed-watchdog metrics at the top level and adds `subprocess`: `p95_ms`, `baseline_p95_ms`, `overhead_ms`, `overhead_budget_ms` (150), `absolute_budget_ms` (300), both sets of batch p95s, in-process p95, correctness and pass status. Both writers preserve the other layer's results, including on a timing failure. CI retains one artifact per OS and prints the installed-watchdog value in the job summary. Dated CI measurements are in the [evidence index](README.md); older runs do not establish a bare-interpreter baseline.

## Saved-case scope

The `hook-latency-budget` case audits supplied measurements without rerunning them. Its assertions distinguish passing samples, equality at either subprocess budget, incorrect output, percentile calculation, unchanged inputs, and the independent no-history-read guard. Direct-child controls include bare-interpreter samples; other layers keep the 150 ms budget. Historical grades describe the policy they evaluated and are not evidence of a fresh run of this revision.

The updated cases have not been executed. Behaviour evidence remains the adjudicated iteration-6 snapshot; runtime microbenchmarks do not establish model behaviour.

Raw historical notes and measurements are withheld outside the public tree. The measurement table records their SHA-256 hashes; sanitized grades and benchmark summaries remain in [the minimal archive](evidence/hook-latency-eval.zip).
