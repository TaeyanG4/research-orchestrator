# v3 — P4 specification: core rewrite, examples, documentation, release

**Version 1.1** (2026-10-25; release version 6.0.0). Parent plan: [v3-plan.md](v3-plan.md) §8–10; follows P1–P3. Branch `v3`.

## 1. SKILL.md core (≤ 12 KB, UTF-8 bytes, enforced by `validate_release.py`)

Contents, in this order: what the skill is (5 lines) · the four files and `.ro/` · setup (choose a preset → user name →
what the preset asks; `--list-presets`) · read order · item lifecycle (claim/own → work → discovery → event →
follow-ups → remove) · one home per fact · the checker and `ro brief`/`ro close` · a table "when setting X is Y, read
references/Z" · safety in one paragraph (what hooks block, how to see warnings). Every rule lives in exactly one file;
the core never repeats a reference.

## 2. References (one topic each; each ≤ 10 KB)

`presets.md`, `workflow-classic.md`, `workflow-unified.md`, `verification.md`, `staged-items.md`, `research-guards.md`,
`competition.md`, `adapters/kaggle.md`, `postmortem.md`, `operations-safety.md`, `hooks.md` (with the capability matrix),
`compute.md`, `git-sync.md`, `migration-v2-to-v3.md`.

## 3. Templates

The generated agents.md holds: the one-line preset summary, the settings block, "read references/…" pointers for the
active settings, and the user-owned `## Project rules` region with three subsections: `Standing rules` (byte budget,
checker WARN when exceeded), `Active overrides` (each with `Expires:`; WARN when expired), `Lessons` (one line each:
`<mistake> → enforced by <check id | none>`).

## 4. Examples (`examples/`)

One small project per preset, generated by init and then filled with a few realistic records, each passing the checker
with 0 ERROR / 0 WARN:
- `quick-script-cleanup` (work; a software chore),
- `work-project-data-migration` (work; a multi-day migration with an external-actions ledger for the production
  cutover and a direction review that uses only the parts that apply),
- `solo-research-literature-replication` (research, **non-ML**: replicating a published statistical result; no
  leaderboard, no labels; guards declared not applicable where they do not fit),
- `team-research-cv-leakage` (the v2 example, upgraded),
- `competition-solo-tabular` (competition; external-actions ledger for submissions, instruments incl. external feedback, a direction review),
- `competition-team-forecasting` (competition, classic workflow, cross-host review).

## 5. READMEs

`README.md` (English, primary) rewritten for v3: why (the three post-mortems in one paragraph), presets table, setup,
the two workflows, guards, safety and hooks, migration from v2. `README.ko.md`, `README.ja.md`, `README.zh-CN.md`
translated from it with the same structure (no drift). Images: keep existing ones that still apply; no new binary assets
required.

## 6a. Writing style (skill-creator guidance)

Explain the reason behind each rule instead of stacking ALWAYS/NEVER in capitals; keep the core lean and remove what
does not pull its weight; references over ~300 lines get a table of contents; the frontmatter `description` says what
the skill does and when to use it, a little "pushy", naming work projects, research and competitions explicitly.

## 6b. P5 — behaviour evals and trigger optimisation (before the final evaluation)

**Superseding owner decision (2026-10-26):** no further scenario runs or description optimisation for 6.0.0. The owner validates in real use. Behaviour evidence is the adjudicated iteration-6 snapshot, not a fresh final-runtime benchmark. The loop below records the earlier plan and is deferred beyond this release. Unit regressions and release gates remain required.

Follow the skill-creator process for an existing skill:
- **Test cases** in `skills/research-orchestrator/evals/<case>/` in the strict skill-creator format (prompt.md,
  case.yaml, graders/, files/). Cases cover all three profiles and the riskiest behaviours, e.g. start a multi-day work
  project from a preset; resume unified research, claim, record a discovery with follow-ups and close; upgrade a v2
  project without losing `## Project rules`; record an external action with an expected outcome; launch and monitor a
  long job; react to a saturated family. Assertions are objective and scripted where possible (checker 0 ERROR, claim
  lines present, rules region byte-identical, ledger entry written before the result, …).
- **Runs**: each case with the v3 skill and with a snapshot of the v2 skill (`old_skill` baseline), in parallel;
  timing and tokens recorded; graded; aggregated into a benchmark; the eval viewer generated for the owner to review.
- **Iterate** on failures (generalise, keep the prompt lean), rerunning into the next iteration directory.
- **Trigger optimisation**: 20 realistic queries (8–10 should trigger across work/research/competition, 8–10 tricky
  near-misses), reviewed by the owner, then the description optimisation loop; apply the best held-out description.
- The benchmark and viewer results are given to both final evaluators.

## 7. Final evaluation

Two Codex reviewer sessions (owner 2026-10-25: Claude usage short, so a second independent Codex reviewer session replaces the Claude reviewer; P5 runs also use Codex, in parallel) each evaluate the finished `v3` branch in an independent session (no shared context with the builders or
each other) against a written rubric and give a score out of 100 with reasons. **Acceptance (owner, 2026-10-25): both
scores ≥ 95.** Below that, the findings become fix items, the fixes go through the usual build → review cycle, and both
evaluate again in fresh sessions; repeat until both reach 95. Rubric (weights): goals of the plan met
(25), correctness and tests (20), generality across domains (15), usability of presets/setup (15), safety without
overhead (15), documentation quality and size discipline (10).
